# Sanity Data Layer

All content lives in **Sanity** (project `8mj49az4`, dataset `production`). The Studio is
`apps/cms` (`@a11y.cool/cms`, deployed to <https://accessibility-cool.sanity.studio>). The site reads
it through `packages/data` (client, queries, generated types, SEO builders) and fetches it with
**SvelteKit remote functions** in `apps/blog`. (Ghost and Directus were replaced by Sanity — none
of their code remains.)

## Architecture

```

├── sanity.config.ts               Studio: structureTool, vision, codeInput; singleton guards
├── sanity.cli.ts                  projectId/dataset/studioHost + `typegen` config
├── structure.ts                   Desk: home / about / siteSettings singletons, then lists
└── schemaTypes/
    ├── index.ts                   schemaTypes[] + singletonTypes
    ├── postType.ts pageType.ts personType.ts categoryType.ts      documents
    ├── homeType.ts aboutType.ts siteSettingsType.ts               singletons (_id = type name)
    └── metaType.ts blockContentType.ts accessibleImageType.ts
        calloutType.ts socialLinkType.ts                           objects

packages/data/
├── schema.json                    ← written by `extract-schema` (commit it)
└── src/
    ├── sanity/
    │   ├── api.ts                 projectId, dataset, apiVersion (public, not secrets)
    │   ├── client.ts              anonymous client: perspective 'published', useCdn, no token
    │   ├── queries.ts             every GROQ query (defineQuery) + SLUG_MAX_LENGTH
    │   ├── sanity.types.ts        ← GENERATED by TypeGen — never edit by hand
    │   ├── image.ts               urlFor, urlForCrop, dimensionsOf, lqipOf
    │   └── meta.ts                resolvePageMeta, shareImageFrom, excerptFromBlocks, truncateAtWord
    ├── seo/
    │   ├── ids.ts                 seoId — every JSON-LD @id, spelled once
    │   ├── entity.data.ts         ENTITY, ENTITY_SENTENCE
    │   └── jsonld.ts              graphContext + homeGraph/aboutGraph/blogGraph/postGraph
    ├── types/*.type.ts            re-exports of TypeGen query result types
    ├── default/metaDefault.data.ts  defaultMetaTags(url)
    └── index.ts                   barrel

apps/blog/src/
├── lib/sanity.server.ts           fetchOr() — the degradation contract
├── lib/content-index.server.ts    getContentIndex() for the crawl files
└── routes/
    ├── data.remote.ts             getSettings, getHome, getAbout, getPage(slug)
    └── blog/data.remote.ts        getPosts, getPost(slug)
```

**There are no fetchers in `packages/data`.** It owns the client, the queries and the types; the
app owns fetching.

## Workflow: Schema → Extract → TypeGen

Types are generated, never hand-written. Any change to a schema type **or** a query needs a regen:

```bash
pnpm generate:types   # = cms extract-schema (→ packages/data/schema.json)
                      #  + cms generate-types (→ packages/data/src/sanity/sanity.types.ts)
pnpm --filter @a11y.cool/cms deploy-schema   # push the schema to the Content Lake
pnpm --filter @a11y.cool/cms deploy          # redeploy the hosted Studio
```

TypeGen scans `packages/data/src/**` for `defineQuery` calls (config: `typegen` in
`apps/cms/sanity.cli.ts`, with `overloadClientMethods: false` — call sites pass the result type).
Commit `schema.json` and `sanity.types.ts` together with the schema/query change.

Schema rules:

- Use `defineType` / `defineField` / `defineArrayMember`
- Content images are `type: 'accessibleImage'`, never a bare `image` — it enforces alt text
- SEO overrides go in a `meta` field (`type: 'meta'`), read through `resolvePageMeta`
- A new singleton: add it to `singletonTypes` in `schemaTypes/index.ts` **and** to `structure.ts`

## Adding a Query

Every query lives in `packages/data/src/sanity/queries.ts`, wrapped in `defineQuery` so TypeGen
names its result `<Name>QueryResult`. Reuse the projection fragments (`imageFields`, `bodyFields`,
`personFields`, `postCardFields`, `livePostFilter`).

```ts
// ✅ packages/data/src/sanity/queries.ts
export const pageQuery = defineQuery(`
	*[_type == "page" && slug.current == $slug][0] {
		_id,
		_updatedAt,
		title,
		"slug": slug.current,
		body[] { ${bodyFields} },
		meta
	}
`);
```

```ts
// ❌ A plain template string — TypeGen never sees it, so there is no result type
export const pageQuery = `*[_type == "page" && slug.current == "${slug}"][0]`;
// ❌ …and interpolating input into GROQ is an injection hole: always pass `$params`
```

- Project only the fields the UI, meta or JSON-LD actually use
- Dereference what you render (`authors[]->{…}`, `asset->{ … metadata { lqip, dimensions } }`)
- Posts always go through `livePostFilter` (slugged and `publishedAt <= now()`)

## Types Live in `packages/data/src/types`

Shared types are **re-exports of TypeGen results**, never hand-written interfaces:

```ts
// ✅ packages/data/src/types/post.type.ts
import type { PostQueryResult, PostsQueryResult } from '@a11y.cool/data/sanity/sanity.types';

export type Post = NonNullable<PostQueryResult>;
export type PostCard = PostsQueryResult[number];
```

```ts
// ❌ Hand-written — drifts from the schema the moment a field changes
export interface Post { title: string; slug: string; … }
```

Inside `packages/data`, modules import each other by package name (`@a11y.cool/data/sanity/client`)
— `vitest.config.ts` aliases that back to `src/`. New type files must be exported from
`src/index.ts`. Never declare shared types in `apps/*`, `packages/ui` or `packages/utils`.

## Fetching: Remote Functions + the Degradation Contract

Fetching happens in `*.remote.ts` files next to the routes, using `query()` from `$app/server`.
Every call goes through `fetchOr()` (`apps/blog/src/lib/sanity.server.ts`), which **never throws**:
on any error it `console.warn`s and returns the fallback (`null` for a document, `[]` for a list).
That keeps the site rendering its empty states when Sanity is down.

```ts
// ✅ apps/blog/src/routes/blog/data.remote.ts
import { query } from '$app/server';
import * as v from 'valibot';
import { postQuery, postsQuery, SLUG_MAX_LENGTH } from '@a11y.cool/data/sanity/queries';
import type { PostQueryResult, PostsQueryResult } from '@a11y.cool/data/sanity/sanity.types';
import { fetchOr } from '#lib/sanity.server.ts';

export const getPosts = query(async () => fetchOr<PostsQueryResult>('posts', [], postsQuery));

export const getPost = query(v.pipe(v.string(), v.maxLength(SLUG_MAX_LENGTH)), async (slug) =>
	fetchOr<PostQueryResult>(`post "${slug}"`, null, postQuery, { slug })
);
```

```ts
// ❌ Throws on an outage → 500 instead of an empty state
export const getPost = query(v.string(), async (slug) => client.fetch(postQuery, { slug }));
// ❌ Unvalidated, unbounded argument — remote functions are public HTTP endpoints
export const getPost = query('unchecked', async (slug) => …);
```

- Every remote function with an argument validates it with valibot; slugs are capped at
  `SLUG_MAX_LENGTH`
- The **route** decides what missing data means — `error(404)` for a missing post, an empty state
  for missing page copy. Remote functions never make that call
- The client has no token and reads only published content, so nothing here is secret — but keep
  fetching in remote functions anyway: one place for the contract, caching and validation

## Universal Loads: Meta + JSON-LD

Pages use **universal `+page.ts`** loads (there are no `+page.server.ts` files) that call the remote
functions, then return `pageMetaTags` and `jsonLd`. Both are declared on `App.PageData` in
`apps/blog/src/app.d.ts`; the root layout renders `<MetaTags>` (deep-merged onto `baseMetaTags`)
and exactly one `<JsonLd>`.

```ts
// ✅ apps/blog/src/routes/blog/+page.ts
export const load: PageLoad = async ({ url, parent }) => {
	const [{ settings }, posts] = await Promise.all([parent(), getPosts()]);

	const pageMetaTags = resolvePageMeta(null, { title: TITLE, description: DESCRIPTION });
	const jsonLd = blogGraph(graphContext(url, settings), {
		title: TITLE,
		description: DESCRIPTION,
		posts
	});

	return { posts, pageMetaTags, jsonLd };
};
```

**Meta:** always `resolvePageMeta(doc.meta, { title, description, image? })`. Sanity's `meta` wins,
the route's literal is the fallback, empty strings never ship. `description` is required. Share
images come from `shareImageFrom(source, alt)` (1200×630, `fit=crop`).

**JSON-LD rules:**

- **One graph per page**, built by a builder in `seo/jsonld.ts` from `graphContext(url, settings)`
- **Never `deepMerge` a graph** — it replaces arrays wholesale and breaks `@id` references
- `@id`s come from `seoId` only; Person ids are `/about#<slug>` (MemberCard renders that anchor)
- **noindex routes emit no graph** — `/imprint` and `/privacy-policy` set `robots` in the route
  (not the Studio) and return no `jsonLd`

```ts
// ❌ Merging a page graph into a site graph
const jsonLd = deepMerge(siteGraph, { '@graph': [articleNode] });
```

Site-wide `settings` is loaded once in `+layout.server.ts` (`getSettings()`) — read it via
`parent()`, don't re-fetch.

## Portable Text, Not HTML

Rich text is Portable Text, rendered by `RichText` from `@a11y.cool/ui` (`@portabletext/svelte`).
Nothing renders CMS content with `{@html}`.

```svelte
<!-- ✅ apps/blog/src/routes/blog/[slug]/+page.svelte -->
<RichText value={post.body} />

<!-- ❌ -->
{@html post.body}
```

`RichText` maps: `h2`–`h4` → `RichTextHeading` (slugified `id`, self-link), `link` /
`internalLink` → `RichTextLink` (href through `safeHref` from `@a11y.cool/utils`; unsafe schemes
render as plain text), `code` → `RichTextCode` (`CodeRender`), `callout` → `RichTextCallout`,
`accessibleImage` → `RichTextImage`. `h1` falls back to a paragraph — the route owns the only `<h1>`.
A new block or mark type needs a component **and** an entry in that map.

## Images and Alt Text

- Build URLs with `urlFor(source, width?, height?)` / `urlForCrop(source, w, h)` and size with
  `dimensionsOf(source)` — all from `@a11y.cool/data`. They return `''` / `undefined` when there is
  no asset, so guard with `{#if urlFor(image)}`
- `accessibleImage` can't be published without `alt` unless `decorative` is set. Render
  `alt={image.decorative ? '' : (image.alt ?? '')}`
- Images are served from `https://cdn.sanity.io` — the only extra `img-src` in the CSP

## Crawl Files

`/sitemap.xml`, `/llms.txt` and `/rss.xml` (`+server.ts`) are all built from **one**
`contentIndexQuery` via `getContentIndex()` in `#lib/content-index.server.ts`, then rendered by the
pure `renderSitemap` / `renderLlmsTxt` / `renderRss` in `packages/utils/src/`. They send
`CRAWL_CACHE_CONTROL`. The sitemap lists **indexable pages only**; blog URLs and the feed follow
`isBlogEnabled()`. `static/robots.txt` allows every crawler, AI included.

## Checklist: Adding a Field or Content Type

1. **`apps/cms/schemaTypes/`** — add/extend the type; register it in `index.ts` (and `structure.ts`
   for a singleton). Images → `accessibleImage`; SEO → `meta`
2. **`packages/data/src/sanity/queries.ts`** — add/extend a `defineQuery` projection
3. **`pnpm generate:types`** — commit `schema.json` + `sanity.types.ts`
4. **`packages/data/src/types/`** — re-export the result type; add to `src/index.ts`
5. **`apps/blog/src/routes/…/data.remote.ts`** — `query()` + valibot + `fetchOr`
6. **`+page.ts`** — call it, return `pageMetaTags` (`resolvePageMeta`) and a `jsonLd` graph (or
   none, for noindex)
7. **`+page.svelte`** — render with `@a11y.cool/ui`; rich text through `RichText`
8. Crawl files / `seo/jsonld.ts` if the page is indexable
9. `pnpm --filter @a11y.cool/cms deploy-schema` once the schema change is merged
10. Verify:

```bash
pnpm lint && pnpm --filter a11y.cool-website check && pnpm check-types
pnpm test:unit                                     # data (meta, jsonld), utils (crawl renderers), blog
pnpm --filter a11y.cool-website test:integration   # Playwright SEO suite (tests/seo.spec.ts)
```
